Guía práctica orientada a competencias. Tres partes: (1) cómo usar IDA, (2) qué tipo de archivo es cada cosa y con qué se ataca, (3) trucos para encontrar flags.

## PARTE 1 — IDA (lo básico y lo útil en CTF)

### Qué es y qué hace

IDA (Interactive Disassembler) convierte un binario compilado (código máquina) en ensamblador legible, y con el decompilador (Hex-Rays) en pseudo-C. Sirve para **entender qué hace un programa sin tener su código fuente**.

**IDA Free** decompila x86/x64 desde la versión 8.x — suficiente para la mayoría de retos. Para ARM/MIPS y otras arquitecturas necesitas IDA Pro o usar Ghidra (gratis, decompila todo).

### Atajos de teclado imprescindibles

|Tecla|Acción|Cuándo lo usas|
|---|---|---|
|**F5**|Decompilar a pseudo-C|Lo primero SIEMPRE. Ensamblador es lento de leer|
|**Espacio**|Alterna vista grafo / texto|El grafo muestra el flujo de decisiones|
|**N**|Renombrar variable/función|Vas poniendo nombres a lo que entiendes|
|**X**|Cross-references (quién usa esto)|"¿Quién llama a esta función?"|
|**G**|Ir a una dirección|Saltar a un offset concreto|
|**;**|Añadir comentario|Anotar lo que descubres|
|**Esc**|Volver atrás|Como el "back" del navegador|
|**/**|Comentario en el pseudo-C (F5)|Anotar en la vista decompilada|
|**Tab**|Cambia entre ensamblador y pseudo-C|Ver ambas a la vez|
|**Ctrl+X**|Xrefs hacia (quién apunta aquí)|Rastrear el origen de un dato|

### Ventanas que se usan en CTF

- **Functions window** (izquierda): lista de funciones. Busca nombres como `main`, `check`, `verify`, `flag`, `secret`, `win`, `decrypt`.
- **Strings window** (Shift+F12): **la primera parada de cualquier reto**. Lista todas las cadenas de texto del binario. Aquí aparecen flags en claro, mensajes de "correcto/incorrecto", nombres de archivos, formatos de printf.
- **Imports** (Ctrl+F7 o pestaña Imports): funciones de librería que usa. `strcpy`, `gets`, `system`, `strcmp` te dicen muchísimo sobre qué tipo de reto es.
- **Hex View**: los bytes crudos. Para ver datos embebidos.

### Flujo de trabajo típico

1. **Abre el binario**, deja que IDA termine el auto-análisis.
2. **Shift+F12** → mira las strings. Si la flag está ahí, terminaste.
3. Ve a **`main`** en la Functions window. Doble clic.
4. **F5** para decompilar. Lee el pseudo-C.
5. Identifica la **comparación clave**: casi todo reto de reversing tiene un `if` que compara tu input con algo. `strcmp`, `==`, un bucle que verifica byte a byte.
6. **Renombra (N)** las variables según entiendes: `v3` → `input_usuario`, `v5` → `clave_esperada`.
7. Sigue la lógica hacia atrás desde la comparación: ¿de dónde sale el valor correcto?

### Qué SÍ puedes analizar en IDA

- Binarios ELF (Linux) y PE (Windows), .so, .dll
- La lógica de validación de una clave/flag
- Algoritmos de cifrado/ofuscación caseros (XOR, sumas, rotaciones)
- Buffer overflows: ves el tamaño del buffer y las funciones inseguras
- Constantes hardcodeadas (claves, offsets, magic numbers)

### Qué NO es para IDA (usa otra cosa)

- **Ejecutar el binario y ver qué pasa** → eso es debugging dinámico: `gdb` (con pwndbg/gef), o el debugger de IDA (F9)
- **Explotar el overflow en vivo** → `pwntools` (Python)
- **Bytecode de Python (.pyc)** → `decompyle3`, `uncompyle6`
- **Java (.class, .jar)** → `jd-gui`, `jadx`, `procyon`
- **.NET (C#)** → `dnSpy`, `ILSpy`
- **Ofuscación pesada / packers** → primero desempacar (`upx -d`), luego IDA

## PARTE 2 — Clasificación de archivos y con qué atacarlos

**La regla de oro: SIEMPRE empieza con `file` y `binwalk`.** El tipo de archivo decide la herramienta. Atacar con la herramienta equivocada es la causa nº1 de perder horas.

### Cómo identificar un archivo

```bash
file archivo            # tipo por magic bytes
binwalk archivo         # busca archivos embebidos dentro
xxd archivo | head      # primeros bytes en hex (magic number)
exiftool archivo        # metadatos
strings -a archivo | less  # todas las cadenas de texto
```

### Los magic bytes más comunes (primeros bytes del archivo)

|Bytes (hex)|ASCII|Tipo|
|---|---|---|
|`7F 45 4C 46`|`.ELF`|Ejecutable Linux|
|`4D 5A`|`MZ`|Ejecutable Windows (PE)|
|`50 4B 03 04`|`PK..`|ZIP (o docx, jar, apk, xlsx...)|
|`89 50 4E 47`|`.PNG`|Imagen PNG|
|`FF D8 FF`||Imagen JPEG|
|`47 49 46 38`|`GIF8`|Imagen GIF|
|`25 50 44 46`|`%PDF`|Documento PDF|
|`52 61 72 21`|`Rar!`|Archivo RAR|
|`1F 8B`||Gzip|
|`49 44 33`|`ID3`|MP3 con tag|
|`52 49 46 46`|`RIFF`|WAV / AVI|

### Tabla maestra: tipo → qué es → con qué se analiza

#### Ejecutables (Reversing / Pwn)

|Tipo|Qué es|Herramientas|
|---|---|---|
|**ELF**|Binario Linux|IDA, Ghidra, `gdb`+pwndbg, `objdump -d`, `radare2`|
|**PE (.exe)**|Binario Windows|IDA, Ghidra, x64dbg, `dnSpy` (si es .NET)|
|**.so / .dll**|Librería compartida|IDA, Ghidra|
|**.pyc**|Python compilado|`decompyle3`, `uncompyle6`, `pycdc`|
|**.class / .jar**|Java|`jadx`, `jd-gui`, `procyon`|
|**.apk**|App Android|`jadx`, `apktool`, `mobsf`|
|**.NET .exe**|C#/VB compilado|`dnSpy`, `ILSpy`|
|**WASM**|WebAssembly|`wasm2wat`, `wabt`|

#### Imágenes (Esteganografía / Forense)

|Tipo|Herramientas|
|---|---|
|**PNG**|`zsteg`, `stegsolve`, `binwalk`, `pngcheck`, `exiftool`|
|**JPEG**|`steghide`, `stegseek`, `exiftool`, `binwalk`, `jsteg`|
|**GIF**|`stegsolve`, análisis frame por frame, `identify -verbose`|
|**BMP**|`zsteg`, `stegsolve`|

#### Audio (Esteganografía / Forense)

|Tipo|Herramientas|
|---|---|
|**WAV**|Audacity (espectrograma), `sonic-visualiser`, `wavsteg`, DTMF/Morse|
|**MP3**|`ffmpeg` → WAV, `exiftool`, `binwalk`|

#### Documentos y contenedores

|Tipo|Qué es|Herramientas|
|---|---|---|
|**PDF**|Documento|`pdf-parser`, `pdfinfo`, `pdfimages`, `binwalk`, `strings`|
|**ZIP/RAR**|Comprimido|`unzip`, `7z`, `fcrackzip`, `john` (si tiene contraseña)|
|**docx/xlsx**|Office (son ZIP)|`unzip` y mirar el XML dentro|
|**PCAP**|Captura de red|**Wireshark**, `tshark`, `tcpflow`, `networkminer`|

#### Datos y texto

|Tipo|Herramientas|
|---|---|
|**Texto codificado**|CyberChef, `base64 -d`, `xxd`, dCode|
|**Hash**|`hashcat`, `john`, hashes.com, crackstation.net|
|**Cifrado clásico**|CyberChef, dCode, `quipqiup` (sustitución)|

### Regla de decisión rápida

```
¿file dice ELF/PE?        → REVERSING/PWN → IDA/Ghidra
¿file dice imagen?         → STEGO → zsteg/steghide/stegsolve + binwalk SIEMPRE
¿file dice audio?          → STEGO/FORENSE → Audacity espectrograma
¿file dice PDF/ZIP/Office? → FORENSE → binwalk, extraer, mirar dentro
¿file dice pcap?           → NETWORK → Wireshark
¿es texto raro?            → CRYPTO → CyberChef Magic, dCode
¿file dice "data"?         → binwalk -e y xxd, algo está oculto o es raw
```

**Y pase lo que pase: `binwalk archivo` y `strings -a archivo`.** Muchísimos retos esconden un ZIP dentro de un PNG, o la flag en claro dentro de un binario.

## PARTE 3 — Trucos para encontrar flags en reversing

### Lo primero, siempre

```bash
strings -a binario | grep -iE "flag|cidsi|ctf|\{.*\}|secret|password|key"
```

Si la flag está hardcodeada en claro, esto la encuentra en 2 segundos. **Pruébalo antes de abrir IDA.**

### Strings con codificación

A veces la flag no está en ASCII directo:

```bash
strings -e l binario    # UTF-16 little-endian (típico en binarios Windows)
strings -e b binario    # UTF-16 big-endian
strings -n 4 binario    # cadenas de mínimo 4 caracteres
```

### En IDA: buscar la comparación

1. Shift+F12 → busca strings tipo "Correct", "Wrong", "Access granted", "Try again".
2. Doble clic en esa string → X (xref) → te lleva al código que la usa.
3. Justo antes hay un `strcmp`, `memcmp` o un bucle de comparación. Ahí está la lógica.

### Patrones de ofuscación casera (muy común en CTF)

Los retos suelen "cifrar" la flag con operaciones simples que se revierten fácil:

- **XOR con clave fija**: `flag[i] ^ 0x42`. Buscas la clave en el código y aplicas el XOR de vuelta en CyberChef.
- **Suma/resta**: `flag[i] + 3`. Reviertes restando.
- **Rotación de bits** (`rol`/`ror`): `>>` `<<` en el pseudo-C.

En el pseudo-C de F5, si ves un bucle con `^`, `+`, `-`, `<<`, `>>` sobre un array, eso es la transformación. Cópiala a CyberChef o a un script Python y revierte.

### Funciones que delatan el tipo de reto

|Ves en Imports|Probablemente es|
|---|---|
|`gets`, `strcpy`, `sprintf`, `scanf("%s")`|Buffer overflow (pwn)|
|`system`, `execve`, `/bin/sh`|Buscar cómo llegar a esa llamada|
|`strcmp`, `memcmp`|Comparación de flag/clave|
|`ptrace`|Anti-debugging, hay que saltarlo|
|`fork`, `signal`|Anti-debug o lógica compleja|
|`rand`, `srand`|Semilla predecible, PRNG|

### Debugging dinámico cuando el estático no basta

Si la flag se construye en memoria en tiempo de ejecución:

```bash
gdb ./binario
# con pwndbg instalado:
break main
run
# pon un breakpoint justo después de que se arme la flag
# examina memoria:
x/s $rax        # ver string apuntada por rax
x/20x $rsp      # ver 20 words desde el stack pointer
```

O más simple, `ltrace` y `strace` muestran las llamadas a librería y al sistema en vivo:

```bash
ltrace ./binario    # ve strcmp("tuinput", "LA_FLAG") en claro a veces
strace ./binario    # llamadas al sistema
```

`ltrace` es un truco brutal: si el binario hace `strcmp(input, flag)`, ltrace te imprime **ambos argumentos**, y ahí está la flag sin tocar IDA.
